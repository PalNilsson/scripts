# Core Dump Analyzer

A standalone prototype that runs `gdb` over a core dump, extracts structured
evidence, and asks an Anthropic model to explain what went wrong in plain
language — no gdb literacy required from the reader.

Built as a precursor to a Bamboo MCP tool (`atlas.core_dump_analysis`) for
diagnosing looping and crashing ATLAS/PanDA jobs. See
[Bamboo MCP integration](#bamboo-mcp-integration) for the intended path.

## Why two layers

The script is deliberately split, because only one half is meant to survive into
Bamboo MCP:

| Layer | Function | Responsibility |
|---|---|---|
| **Evidence** | `collect_evidence()` | Drives gdb, normalises, de-duplicates, redacts, truncates. **No LLM awareness.** |
| **Synthesis** | `analyze_with_llm()` | Sends the evidence bundle to Anthropic, parses a structured verdict. |

Run with `--no-llm` to print the evidence bundle alone. That output is exactly
the payload an MCP tool would return, which makes it the fastest way to iterate
on the gdb layer without spending tokens.

## Install

```bash
git clone <this-repo> && cd core-dump-analyzer
pip install -r requirements.txt
```

`gdb` is a system package, not a pip package:

```bash
sudo dnf install gdb        # RHEL / CentOS / AlmaLinux
sudo apt-get install gdb    # Debian / Ubuntu
```

Developed and tested against gdb 15.1 and 16.3. The gdb command set used is
conservative, so older grid worker nodes (gdb 8–12) should also work; anything
unsupported degrades to a recorded warning rather than a failure.

## Usage

```bash
export ANTHROPIC_API_KEY=sk-ant-...
python analyze_core_dump.py core.123456
```

Common variations:

```bash
# Iterate on gdb extraction only — no API call, no tokens spent
python analyze_core_dump.py core.123456 --no-llm

# Force hang framing and keep both machine-readable and raw output
python analyze_core_dump.py core.123456 --mode hang --json evidence.json --raw-gdb raw.txt

# Point at an explicit interpreter build (see the note below)
python analyze_core_dump.py core.123456 --exe /cvmfs/atlas.cern.ch/.../bin/python
```

### Options

| Option | Default | Purpose |
|---|---|---|
| `--exe PATH` | auto | ELF executable to load. **Not** a `.py` script — see below. |
| `--mode {auto,hang,crash}` | `auto` | Analysis framing; `auto` infers from the terminating signal. |
| `--model NAME` | env | Anthropic model override. |
| `--max-frames N` | 40 | Stack frames per thread. |
| `--max-thread-groups N` | 25 | Distinct thread backtraces to retain after grouping. |
| `--max-evidence-chars N` | 50000 | Total evidence budget. |
| `--no-locals` | off | Skip `info locals`. Collected by default. |
| `--no-redact` | off | Disable credential scrubbing. |
| `--gdb PATH` | `$PATH` | Explicit gdb binary. |
| `--gdb-timeout N` | 120 | Per-phase timeout in seconds. |
| `--no-llm` | off | Evidence only; skip the API call. |
| `--json FILE` | – | Write evidence + analysis as JSON. |
| `--raw-gdb FILE` | – | Write unprocessed gdb output. |

### Environment

| Variable | Required | Notes |
|---|---|---|
| `ANTHROPIC_API_KEY` | unless `--no-llm` | – |
| `CORE_ANALYSIS_MODEL` | no | Checked first for the model. |
| `LLM_DEFAULT_MODEL` | no | Fallback, shared with Bamboo MCP. |

Model default is **`claude-sonnet-4-6`**. Symbolised C++ stacks with mangled
template frames need real reasoning to separate the actual bug from framework
noise, and a 40-frame × 25-group bundle is a substantial prompt.
`claude-haiku-4-5` is worth benchmarking via `CORE_ANALYSIS_MODEL` once the
prompt stabilises — hang-mode dumps are structurally simpler (find the busy
thread, name the loop), so if Haiku holds up there it is the better choice for
automated per-failure analysis at scale.

## The `--exe` question: `athena.py` is not a binary

gdb needs the **ELF executable that was running**, not the script. For an
`athena.py` job that is the Python interpreter. Passing `athena.py` to `--exe`
would make gdb report `file format not recognized`, so the script detects a
`.py` argument, ignores it, and falls back to automatic resolution with a note.

The interpreter must be the *same build* the job used — normally the CVMFS/LCG
`python`, not `/usr/bin/python3`. A version mismatch yields a plausible-looking
but wrong stack, which is the worst possible input to an LLM.

Resolution order:

1. `--exe`, if it exists and is not a `.py` file.
2. **`AT_EXECFN` from the auxiliary vector** (`info auxv`). Primary path: gdb reads
   it from a bare core with no executable loaded, and it does not depend on
   `readelf` being able to decode 64-bit notes (some builds cannot).
3. The core's `NT_FILE` note, via `readelf -n`.
4. The `Core was generated by` command line.

An **absolute** recorded path that is missing is reported as unresolved rather
than substituted. If a core references `/cvmfs/.../bin/python` and CVMFS is not
mounted, quietly falling back to a same-named system interpreter would hand gdb
a different build and produce confidently wrong symbols. Only bare names and
relative paths — which the OS would itself have resolved via `PATH` — are searched
for, and any such search is flagged in the warnings.

## Hang vs. crash

These need different gdb emphasis and different prompts, and conflating them is
the main way this kind of tool produces nonsense.

- **Crash** (`SIGSEGV`, `SIGBUS`, `SIGFPE`, `SIGILL`, …): there is a fault to
  explain. Focus on the faulting thread, frame, and memory error.
- **Hang** (`SIGQUIT`/`SIGABRT`/no signal, or a `gcore` snapshot): for a looping
  job the core was produced *deliberately* by the pilot or a watchdog, so there is
  no fault at all. The question is which thread is doing work and why it never
  finishes — infinite loops, deadlocks, lock convoys, pathological allocation.
  If Python frames are available they are usually the most informative evidence.

`--mode auto` infers this from the signal and defaults to hang when no fault
signal is recorded.

## How the evidence is kept small

An Athena job routinely has 100+ TBB/GaudiHive threads parked on the same
condition variable. Sent verbatim that is tens of thousands of near-identical
lines.

- **Thread grouping.** Backtraces are normalised (addresses → `0xADDR`, frame
  numbers stripped) and identical stacks collapse into one group with a count.
  Groups are ranked so working threads come before idle ones.
- **Idle detection.** Stacks topped by `pthread_cond_wait`, futex waits,
  `epoll_wait`, `nanosleep` and similar are flagged `idle` so the model is told
  not to report them as findings.
- **Section markers.** gdb's `echo` emits an explicit marker before each command,
  so per-command output is split exactly rather than guessed at with boundary
  regexes. This matters: an earlier heuristic version silently mislabelled
  `info args` output as `locals`, and feeding a model mislabelled sections is a
  reliable way to get a confident wrong answer.
- **Budgets.** Per-section character limits, then a global cap that sheds the
  least informative thread groups. Anything shortened is recorded in
  `truncated_sections` so the model knows the evidence is incomplete.

Each gdb phase runs as a separate process with its own timeout, so one hanging
command cannot take down the whole analysis.

## Evidence quality warnings

The script actively looks for conditions that make the evidence untrustworthy —
truncated core (a `ulimit -c` cap), core/executable mismatch, missing symbols or
debuginfo, unreadable memory, unresolved executable — and surfaces them at the
top of the report. The prompt instructs the model to lead with these limitations
and lower its confidence rather than guessing, because a confident wrong answer
is worse than "insufficient evidence".

## Redaction

Only gdb *text* is ever transmitted, never raw memory. But `info locals`,
`info args` and mappings can still surface credentials, so a scrubber removes
X509 proxy paths, `x509up_u*` files, JWT-shaped strings, `Bearer` tokens, PEM
blocks, and `*_TOKEN` / `*_PASSWORD` / `*_SECRET` assignments before anything
leaves the process. Disable with `--no-redact`. This is cheap insurance now and a
hard requirement if this ever runs server-side.

Note that `info locals` is **on by default**: for a looping job the loop counters
in the busy frame are often the whole answer.

## Output

Human-readable text to stdout, plus optional JSON (`--json`) carrying the full
evidence bundle and a structured analysis:

```json
{
  "verdict": "...",
  "classification": "crash|hang|deadlock|resource_exhaustion|undetermined",
  "confidence": "high|medium|low",
  "likely_cause": "...",
  "supporting_evidence": ["..."],
  "culprit_component": "...",
  "busy_threads": "...",
  "limitations": ["..."],
  "next_steps": ["..."],
  "explanation": "..."
}
```

If the model returns prose instead of JSON, the raw text is preserved under
`explanation` rather than the run failing.

## Testing

```bash
pip install -r requirements-dev.txt
python -m pytest tests/ -q
flake8 --max-line-length=120 --max-complexity=15 --ignore=W503 analyze_core_dump.py tests/
```

74 tests cover parsing, redaction, thread grouping, mode detection, executable
resolution, prompt construction, JSON extraction, rendering and the LLM path
(with a stubbed SDK). They run without a core file or an API key.

To validate against real cores without waiting for a grid failure:

```bash
bash tests/generate_test_cores.sh /tmp/cores
python analyze_core_dump.py /tmp/cores/core.crash.1234 --no-llm   # crash mode
python analyze_core_dump.py /tmp/cores/core.hang.5678  --no-llm   # hang mode + py-bt
```

The hang fixture is a Python process in an unbounded loop with four idle
threads, so it exercises grouping, idle detection and `py-bt` together. If your
distro intercepts cores via a pipe handler (`systemd-coredump`, `apport`), check
`/proc/sys/kernel/core_pattern`.

## Known limitations

- `py-bt` requires the interpreter's gdb helper on the auto-load path. The
  script sets `set auto-load safe-path /` so CVMFS-hosted helpers load, and
  reports unavailability with a reason rather than failing.
- Detection of unavailable gdb commands relies on stderr; gdb writes
  `Undefined command` there, not to stdout.
- Idle-thread detection is heuristic (a top-frame marker list) and will not
  recognise every framework's wait primitive.
- Symbol quality dominates output quality. Against a stripped binary with no
  debuginfo, the honest answer is "insufficient evidence", and that is what the
  prompt is written to produce.
- Not yet validated against a real ATLAS/Athena core — only synthetic C and
  Python fixtures. Thread-group counts and frame budgets will likely need tuning
  once real Athena cores are available.

## Bamboo MCP integration

Sketch, not yet implemented:

1. **Download.** Extend the existing log-download mechanism (which already
   fetches `pilotlog.txt`, `payload.stdout`) to retrieve `core.NNNNNN` from the
   job log tarball.
2. **Tool.** Register `atlas.core_dump_analysis`, wrapping `collect_evidence()`
   only. The tool returns the evidence bundle; it must **not** call an LLM
   itself.
3. **Synthesis.** Put the mode-specific prompts in `bamboo_executor.py`, where
   every other tool's synthesis prompt lives. Doing it in the tool would pay for
   two LLM calls and lose the shared evidence/citation structure.
4. **Routing.** The usual three-file edit (`bamboo_answer.py`, `planner.py`,
   `bamboo_executor.py`), with signals covering "core dump", "core file",
   "looping job", "segfault", "crashed", "stuck", "hung".
5. **Constraints.** Core files are large and gdb is slow; expect this to be a
   long-running tool needing a generous timeout, and consider whether analysis
   should run on the node holding the core rather than streaming it.

The single biggest open question is **executable availability**: symbol quality
depends on the exact CVMFS release being mounted wherever gdb runs. That is an
environment question, not a code question, and it should be settled before
building the tool.
