# Core Dump Analyzer

A standalone prototype that runs `gdb` over a core dump, extracts structured,
deterministic evidence, and optionally asks an Anthropic model to explain what
went wrong in plain language.

The tool is being developed as a precursor to a Bamboo MCP tool
(`atlas.core_dump_analysis`) for diagnosing looping and crashing ATLAS/PanDA
jobs. The evidence collector is intentionally independent of the LLM layer so it
can later move into MCP without embedding a second model call inside the tool.

## Architecture

| Layer | Function | Responsibility |
|---|---|---|
| **Evidence** | `collect_evidence()` | Runs locally or in a reconstructed ATLAS container, drives GDB, checks Build IDs, normalises/de-duplicates/redacts/truncates evidence. **No LLM awareness.** |
| **Synthesis** | `analyze_with_llm()` | Sends the evidence bundle to Anthropic and parses a structured verdict. |

Run with `--no-llm` while developing or validating the deterministic collector.


## Captured-process identity and symbol trust

For PanDA looping jobs, a core may occasionally belong to the monitoring process rather than the payload. The analyzer therefore records `evidence.process_identity` independently of the GDB symbol interpretation. The core-recorded `Core was generated by` command line is the primary identity signal, corroborated by stack shape when available. A prmon core is classified as `monitor-process-core` and is not given a payload-loop diagnosis.

GDB executable-match warnings and Build-ID coverage are tracked separately from process identity. `0 key modules checked` is reported as **UNVERIFIED**, not as a successful zero-mismatch result. Structured diagnosis confidence is capped when symbol/build identity is degraded.

The deterministic rules currently recognize two post-event-processing XRootD shutdown signatures. They retain detailed classifications but also share a stable family for downstream clustering:

- family `post-event-processing-xrootd-shutdown-hang`, subtype `poller-finalization`: classification `post-event-processing-shutdown-hang`, signature `Py_Exit(0) -> XrdCl::DefaultEnv::Finalize -> PostMaster/Poller::Stop`.
- family `post-event-processing-xrootd-shutdown-hang`, subtype `remote-file-close`: classification `post-event-processing-remote-file-close-hang`, signature `Py_Exit(0) -> TROOT::CloseFiles -> TNetXNGFile::Close -> XrdCl::File::Close -> StreamMutex::Lock`.

## Machine-readable deterministic diagnosis

The evidence layer can emit `evidence.diagnosis` for signatures that are strong
enough to classify without an LLM. This object is intended to be a stable
handoff to Bamboo MCP and deliberately separates the observed failure phase from
an unproven initiating root cause.

For the validated looping-job case it has the form:

```json
{
  "available": true,
  "classification": "post-event-processing-shutdown-hang",
  "family": "post-event-processing-xrootd-shutdown-hang",
  "subtype": "poller-finalization",
  "phase": "process-shutdown",
  "component": "XRootD/XrdCl",
  "confidence": "high",
  "root_cause_established": false,
  "signals": {
    "clean_python_exit": true,
    "xrootd_finalization": true,
    "eventloop_worker_success": true,
    "batch_status_success": true,
    "output_postprocessing": true
  },
  "supporting_evidence": ["..."],
  "limitations": ["..."]
}
```

If the same core-side shutdown signature is present without payload completion
evidence, the classification is `shutdown-finalization-hang` with medium
confidence. Unsupported signatures remain `unclassified`; deterministic rules
must not guess.


## Install

```bash
git clone <this-repo> && cd core_dump_analyzer
pip install -r requirements.txt
```

For local analysis, `gdb` is required as a system package. `eu-unstrip` and
`eu-readelf` from elfutils are strongly recommended because Build-ID identity is
part of the evidence-quality check.

```bash
# RHEL / AlmaLinux / CentOS
sudo dnf install gdb elfutils

# Debian / Ubuntu
sudo apt-get install gdb elfutils
```

For ATLAS-container mode the host also needs CVMFS, ATLASLocalRootBase, and the
normal ATLAS Apptainer setup.

## Basic usage

```bash
export ANTHROPIC_API_KEY=sk-ant-...
python analyze_core_dump.py core.123456
```

Evidence only:

```bash
python analyze_core_dump.py core.123456 --no-llm
```

Force hang framing and retain machine-readable and raw evidence:

```bash
python analyze_core_dump.py core.123456 \
    --mode hang \
    --no-llm \
    --json evidence.json \
    --raw-gdb raw-gdb.txt
```

## ATLAS/PanDA container mode

### Why this mode exists

A core dump is tied to the exact executable and shared-library builds that were
mapped in the process. A same-name executable or a different `libc.so.6` can
produce a plausible-looking but wrong stack.

This was validated on PanDA job `7262157016`, AnalysisBase `25.2.103`. The core
required these system-library Build IDs:

```text
libc.so.6              e650335ac8463e9e58c04e07c6f36c5f826ed953
ld-linux-x86-64.so.2   ea1fffd70b23014f3ac70e84a393f28ea2ac1e66
libm.so.6              2984578f915b2c8cda0fb99d437ae43b2fc06595
```

The original RHEL 9.8 analysis host had different builds and GDB could not unwind
the useful stack. The ATLAS AlmaLinux 9 container resolved to AlmaLinux 9.7 with
matching system-library Build IDs, after which the XRootD shutdown stack unwound
correctly.

### Required job files

The first implementation expects the core and release setup to be under one job
directory that ATLASLocalRootBase mounts as `/srv`:

```text
/path/to/job/
    core.53289
    my_release_setup.sh
    ...other job/log files...
```

`my_release_setup.sh` is the release setup recovered from the job environment.
The original PanDA `container_script.sh` may be kept for reference, but the
analyzer **does not execute it and does not modify it**. In particular, it never
starts the original payload.

### Run in the matching ATLAS container

```bash
python analyze_core_dump.py /path/to/job/core.53289 \
    --execution atlas-container \
    --job-dir /path/to/job \
    --release-setup /path/to/job/my_release_setup.sh \
    --atlas-platform el9 \
    --mode hang \
    --no-llm \
    --json evidence.json \
    --raw-gdb raw-gdb.txt
```

Defaults:

- `--job-dir`: directory containing the core;
- `--release-setup`: `<job-dir>/my_release_setup.sh`;
- `--atlas-platform`: `el9`;
- `--atlas-local-root-base`: `/cvmfs/atlas.cern.ch/repo/ATLASLocalRootBase`;
- `--container-extra-args`: `-c -i`;
- `--container-timeout`: 1800 seconds.

So, when the files have the standard names, the shorter form is:

```bash
cd /path/to/job
python /path/to/core_dump_analyzer/analyze_core_dump.py core.53289 \
    --execution atlas-container \
    --mode hang \
    --no-llm
```

Additional Apptainer arguments can be passed through ATLASLocalRootBase. For
example, the manually validated setup used an extra bind:

```bash
python analyze_core_dump.py /path/to/job/core.53289 \
    --execution atlas-container \
    --container-extra-args "-c -i -B /afs/cern.ch/user/n/nilspal/dev/scripts/core_dump_analyzer/tmp:/tmp" \
    --no-llm
```

That additional `/tmp` bind was useful for the manual investigation but is not
required by the analyzer itself.

### What container mode actually does

The host analyzer:

1. verifies the core, job directory, release setup, and ATLASLocalRootBase;
2. stages a temporary copy of the analyzer plus a small analyzer-owned runner in
   the job directory;
3. calls `atlasLocalSetup.sh -c <platform> -s /srv/<release-setup> -r /srv/<runner>`;
4. runs the evidence collector once inside that container with `--execution local
   --no-llm`;
5. reads the resulting JSON/raw GDB evidence back on the host;
6. removes the temporary worker files unless `--keep-container-artifacts` was
   requested;
7. performs any optional LLM synthesis on the host.

This means the ATLAS container is launched **once per analysis**, while the
GDB evidence phases remain separate subprocesses inside the container. After the
all-thread stack phase, the collector may add one focused `targeted_threads` GDB
phase for selected non-idle thread groups. A slow/hanging GDB command therefore
still has its own per-phase timeout.

### GDB versus the AnalysisBase Python environment

AnalysisBase exports `PYTHONHOME` and `PYTHONPATH` for its Python runtime. On the
validated EL9 container, GDB embeds Python 3.9 while AnalysisBase 25.2.103 uses
Python 3.13. Letting GDB inherit the AnalysisBase Python variables caused GDB's
embedded interpreter to fail at startup with:

```text
Fatal Python error: init_fs_encoding
ModuleNotFoundError: No module named 'encodings'
```

The analyzer protects GDB in two ways:

1. removes `PYTHONHOME` and `PYTHONPATH` from every GDB subprocess environment,
   while preserving release variables such as `PATH` and `LD_LIBRARY_PATH`;
2. launches GDB with the early initialization command:

```gdb
set python ignore-environment on
```

It also keeps:

```gdb
set auto-load safe-path /
```

so CVMFS-hosted GDB helper scripts can load.

## Executable resolution

GDB needs the **ELF executable that was running**, not a Python script. For an
`athena.py`/`EWRun.py` job this is normally the exact Python interpreter from the
release.

Resolution order is:

1. `--exe`, if it exists and is not a `.py` file;
2. `AT_EXECFN` from `info auxv`;
3. the core's `NT_FILE` note;
4. the recorded `Core was generated by ...` command line.

An absolute recorded path that is missing is never silently replaced with a
same-named system binary. Failed candidates are retained as structured
resolution attempts, but a failed/truncated early candidate does **not** remain
as a stale warning if a later candidate resolves successfully.

For job `7262157016`, `eu-unstrip` identifies the executable as:

```text
/cvmfs/atlas.cern.ch/repo/sw/software/25.2/AnalysisBaseExternals/25.2.103/InstallArea/x86_64-el9-gcc15-opt/bin/python3.13
```

with Build ID:

```text
8f6bd1573d10501aec0c3dd50446da7c9524fb86
```

## Build-ID evidence

When `eu-unstrip` is available, the analyzer runs:

```bash
eu-unstrip -n --core CORE
```

It records the number of mapped modules and compares the core Build ID against
the file currently visible to the analyzer for:

- the resolved executable;
- `libc.so.6`;
- `libm.so.6`;
- `ld-linux-x86-64.so.2`.

A mismatch is a first-class evidence-quality warning because native unwinding and
symbol interpretation may be unreliable even when the path/name looks correct.
The full `eu-unstrip` output remains available in `--raw-gdb`; the normal evidence
bundle keeps the compact comparison rather than hundreds of module lines.

## Shared-library symbol states

The analyzer preserves the distinction made by `gdb info sharedlibrary`:

- `Yes` — symbols were read;
- `Yes (*)` — symbols were read, but full/separate debugging information is
  absent;
- `No` — symbols were not read/available.

`Yes (*)` is **not** treated as an unsymbolised library. Missing full DWARF can
limit `info locals`/source-level inspection, but it is materially different from
having no symbols at all.

## GDB metadata collected

In addition to the normal stacks, arguments, locals, registers, Python frames,
and shared libraries, the deterministic collector now captures:

```gdb
info files
show debug-file-directory
info auto-load python-scripts
```

`info files` can be very large for an ATLAS process, so only a bounded excerpt is
kept in the structured evidence; the full output remains in `--raw-gdb`. GDB
warning lines are also summarized separately.

## Targeted thread/frame inspection

After collecting and grouping all thread backtraces, the analyzer selects up to
three non-idle thread groups by default and chooses the most diagnostic frame in
each. It then performs **one additional batched GDB invocation** containing, for
each selected representative thread:

```gdb
thread <id>
frame <n>
info frame
info args
info locals
```

The selection is based on stack content, not hard-coded thread numbers. For the
validated XRootD shutdown core this naturally selects:

- thread 3, frame 3: `XrdCl::PollerBuiltIn::ShutdownEvents`;
- thread 2, frame 3: `XrdCl::StreamMutex::Lock`;
- thread 1, frame 2: `XrdSys::IOEvents::Poller::SendCmd`.

The bounded results are stored in `evidence.targeted_threads` and are also shown
compactly in `--no-llm` output. If GDB reports symbols read for a library but an
optimized frame still has no recoverable arguments/locals, the report records that
per-frame limitation without treating the whole library as unsymbolized. Use
`--max-targeted-threads 0` to disable this
extra phase or set another small bound when investigating a different core.

## Hang versus crash

These need different interpretation:

- **Crash** (`SIGSEGV`, `SIGBUS`, `SIGFPE`, `SIGILL`, ...): explain the faulting
  thread/frame and memory error.
- **Hang** (`SIGQUIT`, `SIGABRT`, no fault signal, or a deliberate snapshot):
  identify which threads are active/waiting and why termination or progress did
  not complete.

`--mode auto` infers this from the terminating signal and defaults to hang when
no fault signal is recorded.

For the validated PanDA core, the useful native evidence is not a Python crash:
Python had already entered `Py_Exit(sts=0)`. The main thread blocks during XRootD
finalization while other XRootD threads show a stream mutex wait and a concurrent
read-timeout/forced-disconnect path. Payload evidence now strengthens this further:
`payload.stdout` reports `worker finished successfully`, a batch status of
`1 success, 0 failure`, completion of EventLoop retrieval, and output-file
move/rename handling before stdout becomes silent for 2h 06m 16s. The combined
deterministic description is therefore **successful event processing followed by
a post-processing/process-shutdown hang in XRootD finalization**. A single core
still does not prove the exact XRootD lock cycle or establish the concurrent read
timeout as the initiating cause.

## Looping jobs: payload-centric log correlation

For `--mode hang`, the automatic log collector deliberately does **not** use
`pilotlog.txt` as a primary source. A looping job is diagnosed from the payload
state: the useful default sources are:

- `payload.stdout`;
- `payload.stderr`;
- payload/user-generated log-like files below `$JOB/workDir`.

The pilot can later record that it detected a loop, captured a core, or killed
the payload, but those lines describe the pilot's reaction. If pilot evidence is
needed for another failure type, use a non-hang mode or pass it explicitly with
`--job-log pilotlog.txt`.

The collector records each payload file's modification time relative to the core.
A long interval between the final payload-log write and core capture is useful
deterministic evidence for a loop even when the payload log has no timestamps.
It also preserves a bounded, line-numbered tail of the actual payload output.
This matters because shutdown/finalization or summary text can appear after the
last periodic `Processed N events` counter; the latest matched progress line is
therefore not assumed to be the final payload activity.

Runtime matching is intentionally conservative: configuration text such as
`lsetup xrootd`, `root://` entries in catalogs, and identifiers such as
`EventErrorState` are not treated as XRootD/error events. Lower-case prose like
`without any error state set` is not an error severity. Static arbitrary `.txt`
files under `workDir` are not auto-discovered merely because they are text. For
hang analysis, automatically discovered `workDir` logs must also have been active
within two hours of the latest non-empty payload stream; this suppresses old
reference/test logs copied into the job tarball. Use explicit `--job-log` to opt
into an older or unusually named file when it is genuinely relevant.

## Evidence size and thread grouping

Athena/Gaudi jobs routinely contain many identical idle stacks. To keep evidence
bounded:

- frame addresses are normalised and identical thread stacks are grouped;
- waits are classified as `blocked` when deeper frames show meaningful lock, shutdown, finalization, or timeout work; only genuinely parked worker waits are marked idle;
- per-section character limits are applied;
- the canonical deterministic evidence remains complete for the human report and
  `--json`;
- only a deep-copied LLM input is reduced by `--max-evidence-chars` before the
  synthesis call;
- any LLM-input truncation is recorded on that disposable synthesis copy rather
  than corrupting the saved evidence artifact.

Each GDB phase is a separate process with its own timeout so one hanging GDB
command cannot take down the whole collection.

## Redaction

Only GDB text is transmitted, never raw memory. `info locals`, `info args`, and
mappings can still expose credentials, so the collector scrubs X509 proxy paths,
JWT-shaped strings, Bearer tokens, PEM blocks, and common token/password/secret
assignments before evidence can reach the API. Disable with `--no-redact` only
when you explicitly need unredacted local evidence.

repository root; there is no `tests/` subdirectory and no

Install pytest if needed and run:

## Known limitations

- The first container backend assumes the core and release setup are under the
  same `--job-dir` mounted by ATLASLocalRootBase at `/srv`.
- Container selection is explicit (`--execution atlas-container`); automatic
  detection/fallback is intentionally deferred until the explicit path is well
  validated on multiple PanDA jobs.
- Full XRootD DWARF/debug packages are not automatically installed. `Yes (*)`
  remains usable symbol evidence but may limit locals/source inspection.
- `py-bt` still depends on the matching CPython GDB helper being available and
  auto-loaded. Helper availability is separate from executable/symbol/debug-info
  availability.
- Thread-state classification is heuristic, but a top futex/condition-variable wait is no longer treated as sufficient evidence that a thread is idle.
- One core snapshot can expose a deadlock/race pattern but may not be sufficient
  to prove the exact lock cycle or event ordering. For looping jobs, payload
  stdout/stderr and payload-generated logs under `workDir` are the primary
  correlation evidence; pilot termination records are normally reactions to the
  detected loop, not evidence of the payload state that caused it.

## Bamboo MCP integration

Once the standalone collector is stable:

1. retrieve the core plus payload stdout/stderr and payload-generated logs;
2. register `atlas.core_dump_analysis` around the deterministic evidence layer;
3. let Bamboo's host/executor perform synthesis rather than calling an LLM from
   the tool;
4. reuse the ATLAS-container backend when local Build-ID evidence is mismatched
   or the exact release environment is requested;
5. for looping jobs, correlate the core's final state first with payload
   stdout/stderr and user/payload logs under `workDir`; use pilot logs only when
   the failure mode makes pilot behavior relevant or they are explicitly requested.

The matching AlmaLinux 9 / AnalysisBase reconstruction, automated container
backend, focused thread/frame phase, and payload-centric looping-job correlation
have all been live-validated on PanDA job 7262157016. The next useful validation
is breadth: run the collector against additional looping and crashing jobs/releases
to harden the environment-selection and log-provenance heuristics before moving
the deterministic collector into Bamboo MCP.
